Apple Neural Engine · mutable weights · macOS 27

Swap one weight file. The model on the Neural Engine predicts a different token.

A transformer sits resident on the ANE, its base frozen. A small LoRA adapter is the only mutable piece. Swap the adapter and the model's next-token decision changes, while the base is never touched. This is Apple's own on-device adapter-serving mechanism, driven with our own model and our own adapters.

The anatomy

One resident base, a small mutable cluster beside it

When aned compiles the model, the frozen base becomes one kernel section. The adapter, declared mutable, becomes a separate cluster. A swap re-patches only that cluster.

Frozen base

6.8 MB

Compiled once, resident on the ANE. Not in the mutable set, so the swap never rewrites it.

Mutable adapter

512 KB

Declared mutable in the model. Its own kernel cluster, patched from a weight file at swap time.

Trust

path

The ANE trusts the adapter file by its directory (an AppleIntelligence path-prefix), not a content signature. That is what lets our own weights in.

It is a bind, not a live rewrite. Each swap creates a fresh program instance over the resident base and patches the adapter cluster. The base is reused; the adapter is re-bound. It is per-request routing, not editing weights mid-generation.

Why it matters

The same shape, on a full LLM

The toy proves the mechanism. On a real 8B, the economics are the whole point: the base is gigabytes and stays resident, the LoRA is a sliver and is all you swap. Bigger base, better the deal.
